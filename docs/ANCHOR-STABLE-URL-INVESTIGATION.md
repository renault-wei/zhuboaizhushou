# 主播级稳定地址 · 调研结论（R55）

> 背景（`docs/LIVE-ROOM-LOCKING.md`）：抖音的 `room_id` 是**一次直播会话**的编号，商家下播重开就变；
> 而我们的采集连着旧房间时**看起来一切正常**（connected、无错误、台本照跑）—— 09-18 实测 AI 独自讲了 15 分钟。
> 当时列的 P1 是：**调研「主播级稳定地址」是否真的永远指向当前直播** —— 成立就能**自动换房间**，彻底解决。
> 本文是那次调研的结论。**结论是否定的**，但过程中确认了一件重要的事，见 §3。

---

## 1. 调研方法

在云端（Huawei Cloud，非家庭 IP）用普通浏览器 UA 直接抓取三种候选形态，看能否拿到「当前房间号」：

| 候选 | 地址形态 | 假设 |
|---|---|---|
| A | `https://www.douyin.com/user/<sec_user_id>` | 主播主页，若能读出「直播中 + 房间号」即可 |
| B | `https://live.douyin.com/<sec_user_id>` | 把主播身份当房间号传，看是否被识别 |
| C | `https://live.douyin.com/<已知房间号>` | **对照组** —— 已知能打开的正确形态 |

主播身份取自库里已存的两条真实分享链接（展开后提取 `sec_user_id`）：

```
v.douyin.com/Mgr6M_ggVrY → reflow/7686410914085620480  sec_user_id=MS4wLjABAAAA597ONoD_4kwAY...
v.douyin.com/nttQ23-DGmE → reflow/7686822988301470479  sec_user_id=MS4wLjABAAAAo5mo95UUXE9q...
```

---

## 2. 结果：**三条路都不通**

```
A. douyin.com/user/<sec_uid>     http=200  72KB
   → 返回的是一个 JS 反爬壳：
     <html><head></head><body></body><script>var glb;..._$jsvmprt=function(b,e,f){...
   → 正文是混淆脚本，**拿不到任何主播数据**、也读不出「是否在播」   ✗

B. live.douyin.com/<sec_uid>     http=200  946KB     md5 9bafdb3a…
   → 页面里【没有】该主播的房间号、【没有】主播昵称
   → 只有 1 处 'room_id' 字样，是页面骨架的通用字段，不是真房间   ✗

C. live.douyin.com/<房间号>       http=200  944KB     md5 ede8ea1a…  （对照组）
   → 页面里【有】房间号 7686822988301470479                       ✓
```

**B 与 C 都不是同一份字节**（md5 不同），但差异来自随机脚本/时间戳，**不含主播信息** ——
关键判据不是 md5，而是这一条：**`live.douyin.com/` 这个形态认的是「房间号」，不是主播身份。**
把 `sec_user_id` 塞进去，服务端照样吐一个通用外壳，但它**不是这位主播的直播**。

> ⚠️ 这一条如果只看「HTTP 200 + 页面很大」会得出**相反的结论** ——
> 这是本次调研最容易踩的坑：**200 ≠ 找对了**。必须核验页面里有没有**这位主播/这个房间**的痕迹。

---

## 3. 但顺带确认了一件重要的事：`sec_user_id` 确实是主播身份 ✓

两条**不同的**分享链接（展开后连房间号都不同），`sec_user_id` 却**逐字符相同**；
而 `share_user_id`（分享者）在两条链接里是不同的。

```
分享链接1：sec_user_id=MS4wLjABAAAAo5mo95…   share_user_id=92503310531
分享链接2：sec_user_id=MS4wLjABAAAAo5mo95…   share_user_id=2208231677761131   ← 分享者变了
                 ↑ 主播身份没变
```

**所以 R51 把 `sec_user_id` 存成 `danmaku_anchor_id` 是对的** —— 它确实是「同一个主播换了房间」的判据。
问题不在身份，在于**没有可用的接口拿「这个身份当前在哪个房间」**。

---

## 4. 签名服务也不行

我们唯一能出网查抖音的通道是 AIOBS 签名服务（`DOUYIN_SIGN_ENDPOINT_URL`，默认 `api.aiobs.cn`），
但它只提供 **wss 连接签名**（`createDouyinHttpSigner` → 喂给 `douyinLiveAdapter`），
**没有「按主播查当前在播房间」这类接口** ✗

---

## 5. 结论与建议

### ❌ 「自动换房间」在现有条件下**做不到**

> 拿不到「这个主播现在在哪个房间」，就没法自动把采集挪过去。
> 这条路**到此为止**，不要再投入。

### ✅ 但这恰好证明 R51 的方向是对的

既然换不了，就必须**让商家知道要换** —— 也就是已经做完的两条：

1. **R51 采集零事件告警**：连着但没弹幕 → 黄条 + 「请粘贴新链接后点『换链接』」
2. **R49 换链接**：贴新链接点「换链接」即可切房间（旧会话自动停）

**这两条是把「自动」降级成「一步手动」**，而不是当作没这个问题。
讽刺的是：**R51 的黄条恰好就是「自动换房间」失败时的最佳替代品** ——
它把「AI 独自讲了 15 分钟没人知道」变成「3 分钟就告诉商家该做什么」。

### 🟡 还剩一个未验证的假设（需要你提供信息）

本次只试了 `live.douyin.com/<sec_user_id>`。**还有一种形态没试**：
抖音的**人类可读抖音号**（如 `guoquan123`）—— `live.douyin.com/<抖音号>`。
它和 `sec_user_id` 是两套编号，行为**可能不同**。

**要验证它，我需要一个正在直播的主播的抖音号**（商家主页那张 JS 壳里读不出来）。
如果你能提供锅圈那个主播的抖音号，我可以立刻再测一次。

**但即使它成立，也还有一道坎**：我们得先**拿到**抖音号（主页是反爬壳），
而它只能靠商家手填 —— 那还不如直接让商家贴一次分享链接。

### 🔵 另一条可选路（成本更高，未评估合规）

问 AIOBS 是否有「按主播查在播」的商业接口。
**但按 AGENTS.md 的口径，弹幕采集整体是「仅自用自测」**，扩大第三方能力面需要先过合规评估 ——
在拿到商家明确的合规结论之前，**不建议往这个方向投入**。

---

## 6. 一句话

> **没有主播级稳定地址。** `live.douyin.com/` 认的是房间号；主播主页是反爬壳；签名服务只管 wss。
> 「自动换房间」这条 P1 到此**结案（不做）**，
> 取而代之的是已经落地的 **R49 换链接 + R51 零事件告警** —— 把自动降级成「一步手动 + 及时告知」。
