# 固定回复（FAQ 式应答）· 讨论稿（不执行）

> 状态：**待讨论**（2026-09-17）。用户提问：「是否可以拆解词做固定回复，比如『多少钱？』这种；
> 话本生成后自动拆解出对应的」。
> 本文只做调研与设计讨论，**不动代码**。

## 1. 这件事的价值（先说清为什么值得做）

它一次解决我在 `SMART-REPLY-AUDIT.md` 里审计出的**两个真问题**：

| 现状问题 | 固定回复怎么解 |
|---|---|
| 每条回复都要调 DeepSeek（**花钱**） | 命中即用现成答案，**零 AI 调用** |
| 回复要等 LLM 几秒（**延迟**） | 直接进 TTS，**秒回** |
| 事实型问题（价格/时间/地址）AI 有**幻觉风险** | 固定答案是**确定性的**，不会说错 |
| DeepSeek 抖动 = 观众问题无人应答 | 不依赖第三方可用性 |

**而且它比 AI 回复更"安全"**：把"我家多少钱"这种问题交给 LLM 自由发挥，本来就是风险最高的地方。

## 2. 对标竞品：**它没有这个东西**

对反编译产物全量搜 `关键词 / 固定回复 / 精确回复 / 自定义回复 / keyword / FAQ / 问答`：**0 命中**。
它宣传的"回答客户疑问"全部走服务端 LLM（`api/v1.live/getReply`）。

**所以这条对我们是差异化，不是抄。** 与我们已有的「自定义违禁词」一样，属于**确定性能力**。

## 3. 我们手上已有什么（决定了能做到多好）

### 3.1 `productSnapshot`：**已结构化的商品事实** ⭐

`scripts` 表里已有 `productSnapshot`（jsonb），且 App 侧字段名是**固定的四个**：

```
name（名称） · package（套餐） · price（价格） · sellingPoints（卖点）
```

**这意味着「多少钱」这类问题根本不需要 AI 拆解** —— `price` 字段本身就是答案。

### 3.2 `scripts.content`：AI 生成的话术正文

营业时间、地址、预约方式这类信息通常只在正文里（不在快照里），**这部分才需要拆解**。

### 3.3 落地现状

- 引擎的 `productSnapshot` 已经作为知识喂给 LLM（`knowledge.productSnapshot`）
- 但**没有任何确定性应答能力** —— 全靠模型每次现编

## 4. 设计草案（三层，从最确定到最不确定）

### 第 1 层：结构化直答（零 AI、零幻觉）⭐ 建议先做且只做这层

直接把快照字段映射成固定问法：

| 观众可能问 | 数据来源 | 固定答案 |
|---|---|---|
| 多少钱 / 价格 / 怎么卖 | `price` | "咱家是 {price}" |
| 什么套餐 / 包含什么 | `package` | "{package}" |
| 卖的什么 / 叫什么 | `name` | "{name}" |
| 有什么优惠 / 卖点 | `sellingPoints` | "{sellingPoints}" |

**零拆解风险**：答案不是"猜"出来的，是商家自己填的字段。**这一层可以自动生效。**

### 第 2 层：从话术正文拆解（需要 AI，**必须人工确认**）

从 `content` 里抽「营业时间 / 地址 / 电话 / 预约方式 / 停车」这类**话术里写了但快照里没有**的事实。

**⚠️ 关键红线：拆解结果只能进草稿，商家确认后才生效。** 理由：
自动拆解 = LLM 阅读理解，**它会编**。把"AI 以为的营业时间"直接播给观众，比不回答更糟。

### 第 3 层：商家手写（保底）

商家自己加问法与答案。**必须有这一层**——自动拆解永远覆盖不全。

## 5. 最容易踩坑的地方：**匹配策略**

这是这类系统的成败点，比拆解本身更重要。

### 5.1 同义问法必须成组

观众不会说"价格"，他会说：
`多少钱 / 多钱 / 几块 / 怎么卖 / 什么价 / 贵不贵 / 价格多少`

**一条 FAQ 必须挂一组问法**（不是单个词），否则命中率会低到没意义。

### 5.2 误命中（比漏命中更糟）

观众说"**上次那个多少钱的套餐我买过了**" —— 命中"多少钱"但**语境完全不是问价**。
回答一句"咱家 99 元"会显得像机器人。

**缓解**：命中只作为**高置信候选**，交给上层决定；并且**固定答案要短**（短答错了伤害小）。

### 5.3 优先级：固定回复 vs AI

- **推荐：固定优先**（事实问题用确定性答案），但**仅高置信命中时**
- 低置信 / 未命中 → 回落 AI
- 这就是业界说的 **FAQ-first + LLM 兜底**

### 5.4 把 FAQ 也喂给 AI

未命中而走 AI 时，**把已确认的 FAQ 作为知识一并给它** —— 保证两套路径口径一致，
不会出现"固定回复说 99、AI 说 99 起"的矛盾。

### 5.5 频控

固定回复**也要受频控约束**（否则照样刷屏），但因为不花钱，频次可以比 AI 回复更宽松。
⚠️ 注意：频控竞态（见审计 §1）**对固定回复同样成立**，修 R28 时一并覆盖。

## 6. 自动拆解的触发点（工程决策）

| 方案 | 说明 | 评价 |
|---|---|---|
| 话术生成时顺带拆 | 在 `POST /api/scripts/generate` 里加一步 | ❌ 该路由已有**重写循环**，再加一步更慢、失败面更大 |
| **独立接口 / 异步** | `POST /api/scripts/:id/faq-draft`，商家点「提取问答」才跑 | ✅ **推荐**：生成与拆解解耦，失败不影响话术 |
| 开播时自动 | 开播前提取 | ❌ 开播路径已经很长，不该再挂 |

**推荐：第 1 层跟随话术生成自动落库；第 2 层由商家显式触发。**

## 7. 数据模型草案

```
live_faq（账号级）
  id / user_id
  patterns      text        一条 FAQ 挂多个问法（顿号分隔，与违禁词同口径）
  answer        text        固定答案
  source        varchar     builtin（第 1 层自动） / auto（第 2 层拆解草稿） / manual
  status        varchar     draft（待确认） / active（生效） / disabled
  hits          integer     命中计数（让商家知道哪条真在用）
```

- **账号级**：与用户拍板的「配置放账号级」一致
- `status` 是关键：**自动拆解落 `draft`，绝不直接 `active`**
- `hits` 让商家看见效果（哪些问法真被问了）

## 9. 待你拍板

❓ **D1 · 第 1 层是否自动生效？**
➡️ **推荐是**。它的答案来自商家自己填的字段，不是猜的，没有幻觉风险。

❓ **D2 · 第 2 层（正文拆解）是否必须人工确认？**
➡️ **推荐必须**。自动拆解是 LLM 阅读理解，会编；直接播出去比不答更糟。

❓ **D3 · 命中固定回复后，还要不要走 AI？**
➡️ **推荐不走**（省钱省延迟），但把 FAQ 作为知识留给**未命中**时使用。

❓ **D4 · 一条 FAQ 挂几个问法合适？**
➡️ **推荐 3~8 个**。太少命中率低，太多误命中率高。

❓ **D5 · 误命中怎么兜？**
➡️ **推荐**：固定答案**短**（≤30 字）+ 允许商家在 App 里看到命中记录并删掉坏问法。

❓ **D6 · 与「氛围语」的关系？**
两者都是"确定性文本"，但**触发源不同**（氛围语走空档插播、FAQ 走弹幕提问）。
➡️ **推荐分开建表**，不合并。
