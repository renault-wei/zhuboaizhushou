## 1. 定位修订：手机直接开播为主线（用户口径 2026-09-07）

- 目标商家普遍没有电脑，也不想要额外的成本与工具（不买声卡、不上电脑直播伴侣）。
- 因此产品主线 =「商家用手机直接开播」；电脑线（直播伴侣 + 虚拟声卡）只作为开发期自测 / 自有直播间验收手段，不作为对外交付形态。
- 演示与素材：用自有抖音号承担谈单演示主链路。

## 2. 必须先讲清的物理约束

- 抖音不开放「第三方 App 向正在开播的手机直播注入声音」的接口：单台开播手机 + 零外设时，AI 声音无法干净进入直播间（外放被麦收音属劣质路，不成立）。
- 因此「声音进直播间」必须有一个本地出声端——电脑 / 旧手机助播 App /（若注入盒支持自身回环，见 §9）同一台开播手机的助播 App；常规做法下竞品身边还有第二台出声设备，「单机 + 盒子自成闭环」能否成立取决于硬件回环，需实测定性。

## 3. 竞品硬件情报：USB 小盒本质 = 声卡桥（调研 2026-09-07）

- 竞品口径：一个小「回声器」插在手机 USB。
- 定性：本质是 **USB 音频注入盒 / 微型声卡桥**——把一路音频（AI 语音）伪装成手机认得的「外接麦克风 / USB 音频输入」，抖音开播时把它当麦采集。
- 边界：它只解决「声音怎么进直播间」，不解决弹幕读取（弹幕仍走弹幕助手）；它不是几百元的专业声卡，是十几~几十元量级的音频转接 / 注入件。
- 可用性验证三步（真机）：① 插上开播手机后，系统 / 抖音能把它选为音频输入；② 出声端放测试音，直播间能听到且无回声 / 电流声；③ 支持边充边播。
- 命名歧义：坊间「回声器」也可能指回声效果器 / 回声消除器，需以实物接口为准（有无 3.5mm 输入、有无充电口、插在出声端还是开播端）。

## 4. 面向无电脑商家的三种形态（按成本排序）

| 形态 | 构成 | 新增成本 | 判断 |
|---|---|---|---|
| A 双手机 + 一根音频转接线（推荐） | 开播手机跑抖音；商家自有一台旧手机装「助播」：读弹幕 → AI → TTS 发音，经转接注入开播手机麦口 | 十几~几十元 | 最贴「手机直接开播」，二期按此真机验证 |
| B 单手机 + 我们的小盒子 | 助播 + 音频注入做进自研盒子 | 硬件研发成本高 | 远期方向，暂不做 |
| C 云端虚拟直播 / 推流 | 需要电脑 / 专业推流盒子 / 抖音官方虚拟主播资质 | 高 | 不符合「无电脑小店」，砍掉 |

## 5. 架构共识：采集端 / AI 大脑 / 出声端 三段解耦 + 异步管道

- 采集端（独立 App / 第三方工具 / 未来盒子）：以「观众身份」连入直播间监听弹幕，只读转发、不参与互动；可独立存在并转发到现有弹幕网关（复用 `POST /api/lives/:id/danmaku`，业务侧零改动）。
- AI 大脑（后端）：异步接收弹幕 → 入队 → 决定「回不回 / 何时回」→ DeepSeek 生成 → 火山 TTS 合成。
- 出声端（主播执行线程）：只认播放队列，一条条串行播；弹幕来得多快都不打架，主播可缓冲执行。
- 收益：每段可独立开发 / 替换（换弹幕工具 = 换适配器）；回复不需要即时，可过滤垃圾、合并重复问题、商品 / 价格类优先插队。
- 落地：现有后端本就是该结构，手机线只换「采集端 / 出声端」的载体，不改架构。

## 6. 弹幕助手生态：有成熟成品，可购买 / 复刻（调研 2026-09-07）

- 结论：弹幕读取不必从零造；但成品几乎都是电脑 / 浏览器 / 服务端形态（抖音没有手机端第三方开放接口）。
- 开源清单：`Iebcn.Live`（弹幕语音播报）、`DanmuFree`（抖音弹幕桌面客户端，Releases 可直接下载）、`skmcj/dycast`（弹幕姬，ws 转发到自建后端）、`burgie-china-danmu`（多平台）、`DouyinLiveJava` / `jwwsjlm/douyinLive`（SDK / 独立服务，可嵌后端）。
- 商用 / 免费成品：小葫芦弹幕助手、OBS 弹幕助手（均支持抖音）。
- 与产品最接近的开源参考：`Yinuo0602/Assistant`（读弹幕 + 对接 DeepSeek / 豆包自动回复）。
- 合规口径（不变）：以上仅作调研存档，不作为商家产品通道；自动读取限「自有直播间、小流量、自用自测」（D 候选口径），路径维持 B 人工中转 → C 屏幕 OCR 半自动 → 官方通道（决策 §3 第 10 条 + `docs/COMPETITOR-XCAI.md`）。

## 7. 二期真机验证方案（替换原「电脑 + 声卡盒」草案）

- 目标场景 = 商家真实形态：手机直接开播。
- 做法：自有抖音号手机开播；后端（暂跑电脑，后续下沉为助播 App / 盒子）出声，经一根音频转接线注入开播手机。
- 验收口径：直播间听到火山音色回复 = 手机线通；与一期电脑线共用同一套后端，链路只换出口。
- 暂不采购：不买声卡，不做「电脑 + 声卡盒」形态的二期验证。
- 前置依赖：音频转接线实物 + 华为真机对 USB 音频设备的识别行为（§3 验证三步）。

## 8. 不做清单 / 话术红线

- 不做「单机零外设即可让 AI 声音进直播间」的承诺（平台层不可行，属话术红线）。
- 采集端（助播 App 形态）与自研盒子（形态 B）为后续排期项，本期不写采集代码。
- 商家商业直播若走自动读弹幕，需要平台官方通道或合规申报后再评估，不写入产品承诺。

## 9. 结论定稿：内录盒 = AI 主播的「声音替身」（2026-09-07，承 §3）

- 机制确认：我们 App 播放话术 → 声音不是从开播手机外放出来，而是被盒子收成一路音频 → 伪装成开播手机认得的「外接麦克风 / USB 音频输入」→ 抖音开播时把它当主播麦采集。观众听到的「主播说话声」= AI 语音，等于把「真人开口」替换成「AI 开口」——就声音维度，这就是一个 AI 主播在出声直播。
- 边界：盒子只是「嘴」（出声替身），不是「主播本尊」——它不读弹幕、不生成话术、不合成声音。完整主播链仍是：弹幕（B 人工中转 / 第三方助手）→ DeepSeek 决定回什么 → 火山合成 → App 播放 → 盒子进麦；盒子只替代最后一段的「声卡 / 布线」。
- 三种接法（决定它省多少步）：
  1. 电脑出声 → 盒子 → 开播手机：把已验证的电脑线出口换成硬件盒，开发期自测形态。
  2. 旧手机跑助播 App 出声 → 盒子 → 开播手机：对应「无电脑商家」目标形态（§4 形态 A，转接线升级为注入盒）。
  3. 单手机闭环（开播手机同时跑助播 App，App 声音自己进麦）：需盒子支持「自身回环 loopback」才成立；普通内录盒是「桥」不是「回环」，买来必须实测（按 §3 验证三步 + §7 口径）。
- 商品文案翻译：手机静音录屏 / 屏蔽手机外音 / 去除直播杂音 = 开播手机不出声、不收环境噪音，只留盒子注入的干净音轨 → 观众听到的纯粹是 AI 话术，不掺真人环境声。
- 对本产品含义：声音替身成立后，「真人插话闪避 / 一键静音 / 真人接管」（G5 待续项）仍是必要播控——真人开口时暂停 AI，避免同一条麦上打架。
- 话术红线不变：不做「单机零外设即可让 AI 声音进直播间」的承诺；单机 + 盒子是否成立取决于硬件回环实测，未通过前对外口径保持为「需出声端（电脑 / 旧手机）注入」。
