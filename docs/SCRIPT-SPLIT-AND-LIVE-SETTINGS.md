## 需求 ①：话术拆分段数

### 1.1 定位：你的观察**完全正确**，而且原因很具体

事实链条（代码）：

| 位置 | 事实 |
|---|---|
| `services/loopScript.ts:16` | `DEFAULT_LOOP_ITEM_COUNT = 6` |
| `services/loopScript.ts:15` | `MAX_LOOP_ITEMS = 12`（硬上限） |
| `routes/loopScripts.ts:228` | `let itemCount = DEFAULT_LOOP_ITEM_COUNT;` —— 请求体没带就用 **6** |
| `routes/loopScripts.ts:229-237` | 带了才用，且校验 1~12 |
| `services/loopScript.ts:238` | 提示词：`把下面这段口播话术改写成 ${itemCount} 条左右的循环台本短句` |
| **`app/lib/core/network/api_client.dart:484`** | **接口有 `itemCount` 参数** |
| **App 各页面** | **没有任何一页传这个参数**（只有列表页在**显示**条数） |

**结论：App 从来不传 `itemCount` → 服务端永远用默认 6 → 商家拿到的永远是 6 段。**

所以「最高 6 段」不是上限，而是**默认值被唯一使用了** —— 真正的硬上限是 12，只是没人碰得到。

### 1.2 为什么当初定 6 / 12

`DEFAULT_LOOP_ITEM_COUNT = 6` 是 **AI 生成的建议口径**（注释：「默认生成 6 条；每条 15-80 字是 **AI 生成的建议口径**，代码只保上限」）。
`MAX_LOOP_ITEMS = 12` 是**防模型跑飞**的安全阀。

**它们本来是给「AI 生成」用的，却在「用户提供话术拆分」这条路上被当成了业务限制。**

### 1.3 讨论：放开之后会发生什么（这才是要拍板的）

**① 「一段话术」和「一本循环台本」本来就是两种东西**
话术 = 一段完整口播（讲清楚商品）；台本 = 可循环的短句（反复播）。
拆得越细，单条越短，**越容易丢语义完整性**（一句话被拆成两半，连着播才通顺，循环到一半就断章取义）。
➡️ **所以「不限制段数」不等于「拆得越多越好」。**

**② 段数直接影响「一轮」的长度**
一轮时长 ≈ 段数 × 单条时长。按默认语速 -10（≈4.7 字/秒）：

| 段数 | 单条 60 字时的一轮时长 |
|---|---|
| 6 段 | ≈ 77 秒 |
| 12 段 | ≈ 2.5 分钟 |
| 30 段 | ≈ 6.4 分钟 |
| 60 段 | ≈ 12.8 分钟 |

**这跟 R42 的「轮次完整性」直接相关**：一轮越长，观众在一个轮次里听到的越完整，但**轮与轮之间的重复周期也越长**（观众可能等不到第二轮）。

**③ 真实的长话术有多长？**
商家上传/生成的团购话术通常 300~1000 字。按 60 字/条拆，大约是 **5~17 段** —— 也就是说 **12 段的上限偶尔真的会卡住人**，而 6 段的默认**经常卡**。

### 1.4 我的建议（供拍板）

| 方案 | 说明 | 评价 |
|---|---|---|
| **A 只放开上限** | `MAX_LOOP_ITEMS` 12 → 更大（如 60），默认仍 6 | 简单，但默认仍是 6，**问题没解决** |
| **B App 让用户选段数** | 加一个「拆成几段」选择器（6/12/24/自定义） | 直接，但把选择负担给了商家 |
| **C 按字数自适应** | 不设段数上限，按「每条目标字数」自动算段数（如每条 40~60 字） | ✅ **最符合「不限制拆分」的诉求，商家不用管段数** |
| **D C + 上限安全阀** | C 的基础上保留一个**很宽松**的上限（如 60 段）防异常输入 | ✅ **推荐** |

➡️ **推荐 D**：语义上「不限段数」，工程上留一个「拦异常」的安全阀（与 R18 放宽字数时同一个思路 —— **安全上限 ≠ 业务限制**）。

## 需求 ②：开播设置保存（含弹幕采集 URL）

### 2.1 定位：现在到底保存了什么

`lives` 表已持久化的字段（14 个）：

```
title              标题
videoSourceUrl     实景画面源
couponId           团购券
rtmpUrl            推流地址（当前不接）
volcPresetId       预设音色
speechRate         口播语速
autoEndMinutes     定时关播（R26 新增）
voiceId            克隆音色
scriptId           话术
loopScriptId       循环台本
status / aiBadgeShown / startedAt / endedAt
```

App 的场次表单实际会提交的：`volcPresetId / speechRate / voiceId / scriptId / loopScriptId`（+ 标题）。

### 2.2 ⚠️ **弹幕采集的 URL 完全没有落库**

```ts
// services/liveCollector.ts:206
const bindings = new Map<string, LiveCollectorBinding>();   // ← 纯内存
```

- 表里**没有** `danmaku_source_url` / `danmaku_room_ref` 这样的列
- `live_danmaku.room_ref` 是**每条弹幕行**上的字段，不是场次配置
  
**后果（都是用户能直接感觉到的）**：

1. **每次开播都要重新粘一次分享链接**（工作台采集卡里粘）
2. **服务重启后绑定消失** —— 正在直播的场次采集直接停（这正是遗留里的 **R17**）
3. 换个手机 / 换个账号看工作台，采集卡是空的

### 2.3 需要保存的项目清单（我的建议）

| 项目 | 现状 | 建议 |
|---|---|---|
| 标题 / 音色 / 话术 / 台本 / 语速 / 定时关播 | ✅ 已存 | 保持 |
| **弹幕采集原始链接** | ❌ **未存** | ✅ **存原文**（商家看得懂、可编辑） |
| **弹幕采集解析结果（roomRef）** | ❌ 未存 | ✅ **也存**（省掉每次重新解析；解析要出网、可能失败） |
| 采集平台（douyin） | ❌ 未存 | 🟡 可存（将来多平台时有用） |
| 采集开关（本场是否启用采集） | ❌ 未存 | 🟡 建议存（避免每次开播都要去工作台点一下） |

### 2.4 讨论点

**① 弹幕 URL 的归属：场次级 还是 账号级？**
- **场次级**（跟着这场直播走）：不同场次可能播不同直播间；与「开播设置」的语义一致
- **账号级**（一个商家一个直播间）：填一次永久生效，最省事
➡️ **我倾向场次级 + 账号级默认值**（新建场次时预填上一次用过的链接）。这样「换直播间」和「不重填」两个诉求都满足。

**② 存原文还是存 roomRef？**
➡️ **两个都存**。原文给商家看/改；roomRef 是解析结果，能省掉每次开播的一次出网解析（解析失败过几次，这一点很重要）。
**但要注意**：roomRef 可能过期（直播间会换房间号），所以**每次开播仍应以原文重新解析为准**，roomRef 只做「解析失败时的兜底」与「展示」。

**③ 改 URL 之后要不要自动重连？**
➡️ 推荐**要**：保存新链接 → 若本场正在采集 → 自动停旧会话、按新链接重连（否则商家改了链接却还在采旧房间，最容易迷惑）。

**④ 这与 R17（绑定表脱离内存）是同一件事吗？**
**是同一件事的两面**：R17 是工程口径（内存 → 持久化），本需求是产品口径（开播设置要记住）。
➡️ 建议**合并成一张票**做，避免分两次改同一块。
