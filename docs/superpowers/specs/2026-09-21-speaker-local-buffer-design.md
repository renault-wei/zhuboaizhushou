# 出声链路简化 · 设计规格

> 日期：2026-09-21　状态：**待用户审阅**（HARD-GATE：未获批准不写实现代码）
> 触发：用户「能否去掉助播机这个模块，感觉没必要，只要能保持声音出来的 keepalive 就可以」
> 澄清结果：① 保留手机出声，把它变成**看不见的保活**；② 方案 **B 为主（本地缓冲）+ A 兜底（原生定时器）**；
> ③ 失败可见性选 **B**（平时一个字不提，真坏了才在工作台显一行红字）。

---

## 1. 背景：问题不是「没拉」，是「拉的节奏」

现有链路（`LIVE_SPEAKER_OUTPUT=phone`，即 docs 里的「手机线」）：

```
服务端合成 wav → 该场次出声队列 remoteSpeechQueue
     → 手机 GET /api/out/speech/next?liveId=xxx → 拉到本地 → 本机播放
```

**2026-09-21 实测故障**（用户「没有声音了，我现在在后台」）：

| 观测 | 值 |
|---|---|
| App 状态 | 后台（visible=false）；STREAM_MUSIC 未静音 |
| 助播机拉取间隔 | **8~22 秒**（代码是 Timer.periodic(1000ms)，应为 1 秒）|
| 真交付（HTTP 200） | **0** |
| 服务端日志 | [loopCaster] 出声链路持续繁忙超过 30000ms（疑似助播机未轮询），放弃本次让位 |

**因果链**：

```
① App 切后台 → Flutter 的 Dart Timer 被系统限流（前台服务保得住进程，保不住定时器节奏）
② 拉取从 1 秒变成 8~22 秒
③ 服务端台本每说一句前要等「出声链路空闲」（isBusy = 本场队列还有没被取走的条目）
④ 拉得慢 → 队列长期非空 → 台本反复等满 30 秒让位 → 静音
```

`loopCaster.ts` 的源码注释早已预言此死法：
「（App 被杀 / 断网），队列永远排不空 → isBusy 恒真 → **台本会卡死在这里**」

### 顺带发现（本次一并修）

`liveSpeaker.ts` 注释写「带 liveId 时只算本场」，但**本地出声端**的实现忽略了它：

```ts
pendingCount(_liveId?: string): number {
  return this.player.pendingCount();   // 忽略 liveId → 别场次积压会卡死本场台本
}
```

远程端（remoteSpeechSink → queue.size(liveId)）是对的。pc 模式下这会咬人。

## 2. 目标 / 非目标

### 目标

1. **商家完全不用管出声**：装上 App、开播即有声音；切后台、锁屏也一直有。
2. **界面上去掉「助播机」这个概念** —— 无开关、无常开记忆、无换链接入口。
3. **真坏了要能知道**：平时一个字不提，异常时工作台冒一行红字。
4. 顺带修掉 isBusy 死锁与本地端 pendingCount 忽略 liveId。

### 非目标（明确不做）

- 不换成「电脑出声」（pc 模式）—— 那要求服务端跑在商家电脑上，是部署形态改造。
- 不做主动通知通道（短信/微信/推送）。
- 不引入长连接 / 服务端推送。
- 不改动服务端合成、TTS、台本与回复引擎。

---

## 3. 架构：把「播放」与「拉取」解耦

```
服务端（已有的大部分）
  台本/回复 → 合成 wav → 该场次出声队列
        ↓  【新增】本场待播清单接口（只返回清单，不传字节）
手机（新）
  一次拉走本场【全部待播】→ 逐个下载到本机临时目录
        → 本地播放器顺序播（播完一条删一条）
        → 隔固定节奏再拉一次（拉空就等）
```

**关键性质**：拉取慢或被限流，**不影响正在播的** —— 本地有缓冲，够连续播。
队列被一次拿空 → isBusy 自然变假 → 台本不再「让位 30 秒」。

---

## 4. 组件与接口

### 4.1 服务端（小改）

**新增** `GET /api/out/speech/pending?liveId=xxx`，返回形如：

```
{ items: [ { jobId, liveId, createdAt } ], maxBatch: 10 }
```

- 只返回**清单**（不含字节），下载仍复用现有 `GET /api/out/speech/next?liveId=`；
  这样**不新增二进制传输路径**，也不破坏既有交付语义（拉走即视为已出声）。
- 不改变队列的存储与淘汰规则（MAX_REMOTE_SPEECH_JOBS_PER_LIVE 不变）。

**修复** `liveSpeaker.ts` 本地端 pendingCount 按 liveId 过滤。

### 4.2 App（主要改动）

- **本地缓冲队列**：磁盘临时目录（wav）+ 内存索引；pull 与 play 两个独立循环。
- **播放循环**：优先播本地缓冲；缓冲空则回退到「边拉边播」（保持旧行为，不至于完全停）。
- **拉取循环**：先问清单 → 逐个下载 → 入本地缓冲；失败指数退避。
- **去掉管理界面**：助播机卡片（开关 / 常开记忆 / 换链接 / 累计播报）从工作台移除。

### 4.3 Android（A 兜底）

把**拉取循环**下沉到 `AssistantKeepAliveService` 的原生定时器（Handler / AlarmManager），
通过 MethodChannel 把「有新音频」回传 Dart 侧播放。
**仅当 B 实测仍受后台限流时才做**（先做 B，真机验证，不够再上 A）。

## 5. 数据流与边界

| 情形 | 行为 |
|---|---|
| 拉取失败 / 断网 | 指数退避（1s→2s→4s…上限 30s），**不清空本地缓冲** |
| 本地缓冲上限 | 约 10 条 / 10 分钟，超出丢弃**最旧**（宁丢旧的也别停） |
| 场次结束 / 被删 | 清空本地缓冲 + 停两个循环（R53 的自检已有） |
| 播放失败（文件损坏） | 删该条、继续下一条，不整体停 |
| 服务端重启（R59） | 队列与运行时会话恢复；本地缓冲保留继续播 |

---

## 6. 产品面：去掉什么、保留什么

**去掉**（工作台）：助播机开关卡、常开记忆、换链接入口、累计播报计数。

**保留（且只有这一处）**：

> 平时**一个字不提**。仅当「本场在播 + 连续 N 秒没有拿到音频」时，
> 工作台冒出一行红字：「**声音没送出去，AI 说了但直播间听不到**」，恢复正常后自动消失。

阈值沿用服务端已有的心跳（R53 的 speakerSecondsSincePull），建议 **30 秒**。

## 7. 测试

**服务端**
- 清单接口：按场次过滤、空队列返回空数组、不影响既有 /next 语义。
- pendingCount(liveId) 只算本场（本地端）。

**App**
- 拉取与播放解耦：拉取被阻塞时，本地缓冲仍能连续播。
- 断网时不清空缓冲、恢复后续拉。
- 缓冲超限丢最旧。
- 场次消失 → 清空缓冲并停止（R53 既有用例扩展）。

**真机**：前台 / 后台 / 锁屏 / 断网恢复 四态各跑一次，记录**实际拉取间隔**与**是否静音**。

## 9. 风险与未决

| 风险 | 说明 | 对策 |
|---|---|---|
| B 仍不够 | 若限流是「整片暂停」而非「变慢」，本地缓冲也只是拖延 | 真机四态验收；不够再上 A |
| 磁盘占用 | 缓冲 wav 堆积 | 上限 10 条 + 播完即删 |
| 交付语义变化 | 「拉清单」不等于「已取走」 | 清单接口**只读**，交付仍以 /next 为准 |
| 兼容 | 旧版 App 仍轮询 /next | 服务端保持 /next 不变，新旧共存 |

---

## 10. 交付顺序

1. 服务端（清单接口 + pendingCount 修复）→ 部署，旧 App 不受影响。
2. App（本地缓冲 + 解耦 + 去界面）→ 装机。
3. 真机四态验收 → 判定是否还需要 A。
4. 需要则做 A。

## 11. 自审补记

### 11.1 单次拉取不是无限的

§3 写的「一次拉走本场全部待播」不严谨：清单接口单次最多返回 10 条，手机据此分批拉。
措辞应为「一次拉走一批（最多 10 条）」。

### 11.2 「下载即交付」这条语义必须说死

现状是「拉走即视为已出声」（/next 流式返回完成就删 wav）。改成先下载进本地缓冲后，
会出现一个新窗口：手机已下载到缓冲、但还没轮到播，而服务端已认为交付（wav 已删）；
若此时进程崩溃，这条音频就真丢了。

**决定：维持「下载即交付」，不新增播放回执。** 理由三条：

1. 循环口播内容本身反复重复，丢一条下一轮还会说；
2. 引入播放回执要维护「已下载未播放」状态机，复杂度不成比例；
3. /next 语义不变，旧版 App 完全不受影响，新旧可共存。

### 11.3 清单与下载之间被抢占

两条 App 可能同时看到同一条清单项，但下载走 /next，而 take(liveId) 是原子取出，
拿不到就返回空 —— 天然去重，无需额外加锁。
