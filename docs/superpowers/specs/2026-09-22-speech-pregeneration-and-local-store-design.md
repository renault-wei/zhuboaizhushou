# 语音预生成 + 本地囤货 设计规格（R69）

> 日期：2026-09-22
> 状态：待用户审阅（按 brainstorming 规程，未批准不写实现）
> 用户拍板：需求是「开播前准备好语音」+「拉取到本地且可定期清理」，并确认
> 「这两个需求是同一件事」，且「一次做完」。

---

## 0. 一句话

把「台本说一句 → 实时合成一句 → App 拉一句」这条**逐句实时链**，
改成「开播前批量合成 → 队列提前有货 → App 囤到本地 → 后台照播」。

---

## 1. 问题（有实测证据）

### 1.1 逐句实时合成 = 每句一个失效点

现状：`liveSpeaker.speak` 每次都直接调火山合成（`volcTTS.ts:280` 处的 `synth.synthesize`），
**完全不查已存在的 `ttsCache`**。

2026-09-22 凌晨实测：火山返回 `45000030 requested resource not granted`，
**80 条连续失败**，从 22:07 到次日 06:11 **整晚零音频**，直播等于静音。
（根因是火山侧额度问题，已由用户充值解决；但**我们的链路对此毫无抵抗力**。）

### 1.2 队列只有一句深，App 无从囤货

现状：`remoteSpeechQueue` 是「实时产出一句、入队一句」，
App 端 `_buffer` 上限 10 条**且只在内存**（R61 规格 §11.2 的选择）。

后果：后台轮询被系统降频（实测前台 58 次/分 → 后台 3~10 次/分）时，
本地没有库存可顶，**声音随拉取节奏一起断**。

---

## 2. 关键约束（决定方案形状）

### 2.1 服务端「交付即删」

`routes/speechOut.ts` 在交付后删除服务端 wav。
**App 拉走的那个副本是唯一副本** —— 本地删错 = 永久丢音频。
清理策略必须围绕这条设计（见 §4）。

### 2.2 现有新鲜度 20 秒 —— **本方案必须改它**（自审发现的硬矛盾）

R63 加了 `MAX_REMOTE_SPEECH_AGE_MS = 20_000`：超过 20 秒未交付的条目直接丢弃。

**这条与「本地囤货」直接冲突**：队列要深、App 要能一次拉一批，
但 20 秒的存活期会在 App 拉走之前就把它们抹掉。

**为什么当初是 20 秒**：那时是「逐句实时合成」——台本说一句产一句，
一句台词若晚 20 秒还没送出去，台上的循环早把同一件事又说了一遍，重播反而奇怪。

**为什么现在要放宽**：预生成之后，音频是**提前备好**的，
一条 1 分钟前合成的台本句和刚合成的没有任何区别（它本来就是循环里的一句）。
20 秒这个数字是绑在「实时」语义上的，**语义变了它就该变**。

**改法**：存活期改为 **10 分钟**，并且与条数上界（`MAX_REMOTE_SPEECH_JOBS_PER_LIVE`）
一起重新定档 —— 两者共同决定「App 离线后队列能存住多少货」。

**要防的退化**：放宽存活期后，App 长时间不在线会攒下大量条目。
由**条数上界 + App 本地双限**共同兜住；不做「无限增长」。

### 2.3 已存在的可复用零件

- `ttsCache.ts`：完整缓存（键 = userId + voiceKey + textSha256），**设计正确**
- `preview:build`：试听产物的预生成先例（可照搬脚本形态）
- `audio:volc`：火山连通性冒烟脚本（可直接用作开播前体检）
- App 端 `path_provider` 已是依赖，录音模块已有写文件先例

## 3. 服务端设计

### 3.1 合成走缓存（第一步，也是一切的基础）

- `liveSpeaker.speak` 改为：先 `findCachedTtsAudio`，命中直接复用；miss 才调火山，
  成功后 `storeCachedTtsAudio`。
- 效果：同一句话第二次出现**零火山调用**；预生成跑过之后，开播期间**一次都不调**。
- 缓存键已含音色 → **换音色自动 miss**，不会播错声音。

### 3.2 预生成服务

输入：场次 id（据此取绑定的循环台本 + 音色）。
行为：把台本所有句逐句走 §3.1 的路径（命中即跳过），串行执行避免打爆火山 QPS。
输出：`{ total, hit, generated, failed: [{ seq, text, reason }] }`。

### 3.3 触发时机（用户选 C：两者都做）

- **保存 / 编辑台本时**：后台预热（不阻塞保存）
- **点开始直播时**：补漏（只跑未命中的，很快）

### 3.4 开播前体检（这条是安全阀）

- 补漏后若**仍有 failed**，**拦住开播**并明确报出是哪几句。
- 理由：否则失败会推迟到开播后才暴露（今早那次就是），
  商家在直播间里才发现没声音，比开播前被拦住糟糕得多。
- 提供「仍然开播」的知情选择，但默认拦住。

### 3.5 队列深度

预生成之后，队列不再只放「当前这一句」。

**具体做法**：`loopCaster` 在推进台本时，**把本轮后续若干句一并入队**
（提前量 = 一轮台本的条数，受条数上界约束），而不是入队一句就等它被取走。

**为什么必须这样**：App 能囤多少，取决于「队列里此刻有多少」✗。
队列只有一句深，App 再怎么主动拉也只能拉到一句 —— **§4.2 的「前台拉满」会落空**。

**与 §2.2 配套**：提前入队必然让条目在队列里停留更久，
所以 20 秒的存活期必须同步放宽，否则这边刚入队、那边就被过期丢掉。

## 4. App 设计

### 4.1 存储与上限

- 位置：App 私有目录（`getApplicationSupportDirectory()` 下的 `speech_out/`）
- 上限：**条数 60 条 + 总字节 20MB 双限**（单靠条数挡不住大文件）
- 索引：轻量 JSON 清单，每条含 `jobId / liveId / 文件名 / 字节 / 落盘时间 / 已播标记`

### 4.2 拉取策略

- **前台**：拉到上限（尽量囤满）
- **后台**：能拉几条拉几条，不追求满
- 拉取与播放**解耦**（沿用 R61 的架构，但缓冲从内存搬到磁盘）

### 4.3 播放

- **只从本地库取**；本地空时回退去拉一次。
- 播放完成即**标记已播**（不是立即删除 —— 删除交给 §4.4 的统一清理）。

### 4.4 清理（最容易做坏的一节）

规则，按优先级：

| 规则 | 动作 |
|---|---|
| 已播 且 落盘超过 10 分钟 | 删 |
| 不属于任何进行中场次 | 删（场次结束后即可） |
| 未播 但 落盘超过 2 小时 | 删（服务端那份早已过期，留着也不会再播） |
| **触发硬上限时** | **从最旧的【未播】开始删，并记一条告警日志** |

触发时机：App 启动 + 开播前 + 每 30 分钟。

**红线：未播音频在未达硬上限时不得删除。**

---

## 5. 明确不做（YAGNI）

- 不做音频转码 / 压缩（省不了多少，徒增失真与 CPU）
- 不做跨场次共享缓存（同一句话不同场次复用价值低，且会让清理逻辑变复杂）
- 不做客户端预生成（合成必须在服务端，客户端只拉成品）

---

## 6. 测试计划

### 6.1 服务端

- 缓存命中：同一句第二次合成**不调火山**（mock 计数为 0）
- 换音色 miss：换 voiceKey 后**必须重新合成**
- 预生成：部分失败时返回值正确列出 failed
- 开播拦截：有 failed 时**默认开播被拒**

### 6.2 App

- 磁盘缓冲：写入 / 读取 / 索引一致性
- **删除防护（重点）**：未播音频在未达上限时**绝不被删**
- 硬上限：达到上限时按「最旧未播优先」删除并记告警
- 本地优先播放：本地有货时**不发网络请求**
- 场次结束清理：结束后属于该场次的残留被清掉

## 7. 分期（用户要求一次做完，此处分期仅表示实施顺序）

| 阶段 | 内容 | 人天 |
|---|---|---|
| 一 | 服务端：合成走缓存 + 预生成服务 + 触发 | 1.0 |
| 二 | 服务端：开播前补漏与拦截 + 队列提前入队 | 0.5 |
| 三 | App：磁盘存储 + 索引 + 预取 | 1.0 |
| 四 | App：本地优先播放 + 清理策略 | 0.5 |
| 五 | 测试补齐（含删除防护） | 0.5 |
| | **合计** | **3.5** |

---

## 8. 风险与回退

| 风险 | 缓解 |
|---|---|
| 磁盘占用失控 | 双限 + 每 30 分钟清理 + 启动即清 |
| 清理误删未播音频 | 红线规则 + 专项测试 |
| 预生成拖慢台本保存 | 后台预热，不阻塞保存 |
| 开播被拦截引起反感 | 明确报出失败句子 + 提供知情放行 |
| 火山 QPS 被打爆 | 串行合成，不并发 |

所有改动**只追加、不改既有产物语义**；
服务端与 App 可分别回退（缓存是旁路，关掉 `TTS_CACHE` 即回到现状）。
