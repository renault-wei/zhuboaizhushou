# 直播间锁定问题 · 定位（不执行）

> 触发：2026-09-18 一场真实直播（`锅圈59.9`）**AI 独自讲了 15 分钟，一条弹幕都没收到**，商家全程不知情。
> 用户要求：先定位，不动代码。

---

## 1. 现象（实测）

| 时间 | 发生什么 |
|---|---|
| 18:36:55 | 商家开播，采集连上房间 `7676074043690208035`，`openAttempts=1`、0.2 秒连上 |
| ~18:3x | **抖音那边下播重开 → 房间号变成 `7686822988301470479`** |
| 18:36~18:53 | 我们的采集仍连着**旧房间**：`status=connected` 但 `eventCount=0` |
| 18:53:14 | 助播机停轮询（另一件事）；18:56:43 场次被结束 |

**关键**：`connected` 让人以为一切正常，**实际上一条弹幕都收不到**。

---

## 2. 根因：**我们锁错了对象**

新旧两条链接展开后的实测对比：

```
旧: reflow/7676074043690208035  sec_user_id=MS4wLjABAAAAo5mo95UUXE9q4SdValE0jKS--qEwGQ5EfDPOr0K4HHw  share_user_id=92503310531
新: reflow/7686822988301470479  sec_user_id=MS4wLjABAAAAo5mo95UUXE9q4SdValE0jKS--qEwGQ5EfDPOr0K4HHw  share_user_id=2208231677761131
            ↑ 变了                        ↑↑↑ 逐字符完全相同 ↑↑↑                                   ↑ 变了
```

| 概念 | 标识 | 生命周期 | 我们用了它吗 |
|---|---|---|---|
| **主播 / 店铺** | `sec_user_id` | **持久**（重开直播也不变） | ❌ **丢了** |
| 一次直播会话 | `room_id`（reflow 后面那串） | **临时**（下播重开就换） | ✅ **被当成了直播间** |
| 分享这条链接的人 | `share_user_id` | 随分享者变 | ❌ 本来就不该用（见 §5） |

**结论：我们把「一次直播会话」当成了「直播间」。**
抖音的 `room_id` 是**会话级**的，主播才是**持久**的 —— 这是**概念层面的建模错误**，不是实现 bug。

## 3. 更值得说的是：**我们本来拿得到那个身份**

```ts
// collectors/linkResolver.ts —— 解析成功只留这四项
export interface ResolvedRoom {
  platform: DanmakuPlatform;
  roomRef: string;          // ← 只有房间号
  matchedUrl: string;
  connectHints?: { cookie?: string };
}

// collectors/shortLinkExpander.ts —— 展开阶段只回两项
export interface ShortLinkExpansion {
  url: string;
  cookie?: string;
}
```

**`sec_user_id` 在展开阶段就被丢掉了**，尽管它明明白白写在跳转后的 URL query 里。

**所以这不是「拿不到」，是「没留」。**

---

## 4. 这是技术漏洞吗？

分两层回答：

| 问法 | 答案 |
|---|---|
| **安全漏洞？**（泄漏 / 越权 / 注入） | **不是。** 没有任何安全面被打开，纯功能性缺陷 |
| **技术缺陷？** | **是，而且是设计缺陷。** 建模错误 + 数据明明在手上却丢掉；已造成一次真实生产事故 |

**严重程度**：
- **复现条件极普通**：商家中途下播重开（直播中很常见）
- **完全静默**：没有任何提示，商家只会觉得 AI 今天不说话
- **后果直接**：AI 独自讲 15 分钟商品，**无人互动、零转化**

## 5. 同一类错误的**第二次发作**

`config/env.ts:128-131` 记录了高度相似的前科：

```
// UserUniqueId = 采集端的自身身份（SignWss 必填），语义是「我是谁」，与分享链接无关。
// 竞品反编译实证：它把这一个数字写死在客户端，不是从链接里取。
// 我们此前误用分享者的 share_user_id —— 换一条链接身份就变，是语义错误。
```

**两处是同一个错误的两次发作**：把「链接里带的某个 id」当成了「它看起来像的那个身份」。
（一次是把**分享者**当成**自己**；一次是把**会话**当成**直播间**。）

这提示一个更根本的改进：**解析结果里的每个身份字段，都应该在类型里明确标注它「是谁」**，
而不是叫一个含糊的 `roomRef` / `userUniqueId` 就往下传。

## 6. 「应该怎么锁定直播间」—— 正解方向

**锁主播，动态发现房间。**

### 6.1 分层

1. **持久身份** = `sec_user_id`（从解析里就取得到，见 §3）
2. **动态发现** = 一个「这个主播现在在播吗、房间号是多少」的能力

### 6.2 发现能力的候选（**可行性待调研，本文不执行**）

| 方案 | 说明 | 我的初判 |
|---|---|---|
| **(a) 主播级稳定地址** | `live.douyin.com/<抖音号>` 之类是否**永远指向该主播当前直播** | ⚠️ **未验证**。我探到 `live.douyin.com/92503310531` 返回 200/943KB，但那只是 SPA 外壳，**不能证明它指向了直播**，必须实测 |
| **(b) 平台接口按主播查在播** | 如 `webcast/room/web/enter/` 按 web_rid / 主播查当前房间 | ⚠️ 需要参数与签名，**可行性未知**；且踩合规边界（见 §7） |
| **(c) 定期重新展开商家给的短链** | 以为能拿到新房间 | ❌ **不可行** —— 短链指向的是**那一次直播**，重展开还是旧房间。**这条路是死的** |
| **(d) 兜底心跳** | 采集连着但 N 分钟零事件 → 提示商家 | ✅ **不依赖任何平台能力，马上能做** |

> **(c) 值得单独强调**：很容易想到「那我隔一会儿重新展开一次链接不就行了」——
> **不行**。短链是那场直播的快照。这也是为什么今天必须由人重新粘一条新链接才恢复。

## 7. 合规边界（必须一起考虑）

本项目对采集有明确红线（`DANMAKU-COLLECTOR-PLAN` D2.5 合规门 + `linkResolver` 顶部注释）：

> 只做公开链接形态解析，**不请求平台接口、不带登录态、不抓包**。

**(b) 那类「按主播查在播」的接口调用，正好踩在这条红线上。**
所以正解更可能落在 **(a) 主播级稳定地址**（仍属公开链接形态解析）+ **(d) 兜底心跳**。
**(b) 需要先明确合规口径再谈**。

---

## 9. 一句话总结

> **我们锁的是「那一次直播」，不是「这个主播」。**
> 抖音的 `room_id` 是会话级的、下播重开就换；而它的稳定身份 `sec_user_id` **就在我们解析到的 URL 里，被我们丢掉了**。
> 这不是安全漏洞，是一个**可预防的设计缺陷**，而且已经真实造成「AI 独自讲 15 分钟」。
