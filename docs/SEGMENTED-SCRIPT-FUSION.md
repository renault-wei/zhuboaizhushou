# 客户方发来的分段话术 · 应该怎么融合（讨论，不执行）

> 客户方给了一份 8 段结构的直播话术（开场 / 引出商品 / 适用人群和场景 / 产品卖点 /
> 核销注意事项 / 价格福利 / 鼓励下单 / 结束语），用户问：这是不是「回复的一些方式」？怎么融合合适？

---

## 1. 它是什么：**分段式直播台本（流程话术）**，不是回复话术

| | 回复话术 | **这份文档** |
|---|---|---|
| 形态 | 一问一答 | **主播独白** |
| 触发 | 弹幕驱动 | **按直播时序推进** |
| 长度 | 短（≤60 字，我们限过） | **每段 100~300 字，全篇约 1500 字** |

**所以它不是回复话术。** 但它**天然兼任回复口径的来源** —— 见 §2。

---

## 2. 它同时是「回复口径」，而且我们架构本来就支持

回复时 AI 拿到的事实（`services/reply.ts:90-95`）：

```ts
{
  liveTitle,          // 场次标题
  scriptContent,      // ★ 绑定的话术全文
  extraKnowledge,     // 商家补充知识
  productSnapshot,    // 商品快照（结构化字段）
  faqHints,           // 固定回复（价格等）的答案
}
```

**`scriptContent` 就是绑定话术的全文。**

> 所以：这份文档**作为「话术」绑定之后**，里面的数字（59.9 / 门店 109.2 / 5.6 折 /
> 10000 多家门店 / 不用预约·随时可退·过期自动退）**会自动成为 AI 回答的依据**。
> 观众问「多少钱」，AI 就有正确口径可引用 —— **不需要另外写一套回复话术**。

**结论：它首先是台本，但它同时也是回复口径的唯一来源。这两件事不该分开做。**

---

## 3. 8 段 → 我们已有的 kind（几乎 1:1）

我们 `services/loopScript.ts` 早就定义了段落类型：

```ts
export const LOOP_ITEM_KINDS = ['opening','product','coupon','warmup','closing','custom'] as const;
```

| 客户方段落 | 映射到我们的 kind | 备注 |
|---|---|---|
| 开场 | `opening` | ✓ |
| 引出商品 | `product` | ✓ |
| 适用人群和场景 | `product` | ⚠️ **我们没有「人群 / 场景」这一 kind** |
| 产品卖点 | `product` | ✓ |
| 核销注意事项 | `coupon` | ✓ |
| 价格福利 | `coupon` | ✓ |
| 鼓励下单 | `coupon` | ⚠️ **我们没有「促单 / CTA」这一 kind** |
| 结束语 | `closing` | ⚠️ **不能进循环**，见 §4(a) |

**8 段映射到 6 个 kind 是可行的**，但有两个语义被挤压了（人群场景、促单）。
要不要扩 kind 是个产品选择（扩了就与既有台本/竞品口径不一致）。

---

## 4. ⚠️ 三个必须先讨论的问题

### (a) 「结束语」**不能进循环**

> 「还有一会儿就结束直播了，想买的赶紧点赞关注下单……」

这句话**每轮都播会很怪** —— 而我们的 caster 是「一轮播完 → 休息 → 再播一轮」，
进循环就意味着 `closing` **每轮都播一次**。

**我们缺「只播一次」的语义。** 可行的做法：
用「定时关播（`autoEndMinutes`）」推导「最后一轮」（剩余时间 < 一轮时长时才放 `closing`）。
**这条要先拍板，否则导入进去就会出洋相。**

### (b) ⚠️ R46 的「按字数自适应拆分」会把结构拆坏

这份文档约 1500 字。R46 现在的口径是「去空白字数 ÷ 50」→ **约 30 段**。

**8 段的语义边界会全部消失**：「核销注意事项」那 200 字会被切成 4 条，
循环到一半就成了断章取义 —— 而那正是 R46 在提示词里**明确想避免**的事。

➡️ **应该优先「按段落切」**（换行 / 小标题），字数只作兜底。

> 这是 R46 上线后暴露的真实边界：当时只考虑「一段长话术拆成短句」，
> 没有考虑「**自带段落结构的模板**」。

### (c) `[y] 折` 是**没填完的占位符**

「而且现在打[y]折，这折扣力度，简直是给大家送福利！」

这是模板变量没填。我们有 `[昵称]` 替换（氛围语），**但台本 / 话术层没有变量机制**。

➡️ 要么提供变量（券后价 / 折扣 / 门店数 自动注入），要么**至少在导入时校验有没有未填占位符**。
（另外全文有 4 处 `[y]`，说明这份很可能是**模板**而不是成品。）

## 5. 融合方式：三个方案

| 方案 | 做法 | 评价 |
|---|---|---|
| **A 当台本导入** | 按段落拆成 8 条 item，各带 kind，进循环 | 直接可播；但 §4(a)(b) 必须一起解决 |
| **B 当话术绑定** | 整篇作为 `scripts.content`，喂给 AI 做回答口径 | 立刻让回复有正确数字；**但不解决「讲」** |
| **C（推荐）一份文档两处用，且同源** | 话术 = 权威原文；台本**由话术生成**（走既有的 `sourceScriptId` 路径） | 避免「台本说 59.9、回复说 59」 |

### 为什么推荐 C

> **商家最容易出的事故，是台本和回复口径各存一份、迟早不一致。**
> 直播里 AI 一边讲 59.9、一边答 59.9 才对；两处各自维护必然漂移。
> 而我们的台本生成**本来就是从话术来的**（`sourceScriptId`）—— **同源是现成的能力**。

---

## 6. 要向客户方确认的三件事

1. **这是「模板」还是「这一场的实际话术」？**（`[y]` 没填，像模板）
2. **以后会持续给这种带小标题的文档吗？** 如果会，就需要一个**导入解析器**（按小标题切段 + 映射 kind）
3. **「结束语」期望什么时候播？** 每轮结尾 / 只在整场最后

---

## 7. 一句话总结

> 它不是「回复方式」，是**分段式直播台本**；
> 但它作为话术绑定后，**全文会自动成为 AI 的回答口径** —— 所以它两件事都干。
> 融合的正解是**一份原文、两处复用且同源**（话术 → 台本），而不是各写一份。
> 落地前必须先解决三件事：**结束语不能每轮播、拆分要按段落、`[y]` 占位符要处理**。
